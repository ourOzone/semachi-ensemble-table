# 배운 것 노트 (백엔드 개편)

> 백엔드·배포·운영을 처음 하며 단계마다 배운 것을 남긴다. 나중에 혼자 운영할 때 찾아보는 용도 (`docs/BACKEND_PLAN.md` "안내 방식").

## B-1 모노레포 (2026-11-27)

**모노레포**: 여러 프로그램(웹·서버)을 저장소 하나에 두는 방식. 반대는 프로그램마다 저장소를 따로 두는 것.
- 좋은 점: 웹과 서버가 같은 타입·스키마를 함께 쓴다(`packages/shared`). API를 바꿀 때 웹·서버를 한 커밋에서 같이 고치고 한 번에 배포한다
- 이 저장소: `apps/`(실행되는 프로그램) + `packages/`(다른 곳에서 가져다 쓰는 코드)

**pnpm workspace**: 한 저장소 안의 여러 `package.json`을 pnpm이 함께 관리하는 기능.
- `pnpm-workspace.yaml`에 패키지 폴더를 적는다 (`apps/*`, `packages/*`)
- 패키지마다 자기 `package.json`(의존성·스크립트)을 갖지만, 설치는 루트에서 한 번(`pnpm install`), 잠금 파일(`pnpm-lock.yaml`)도 루트에 하나
- 패키지 이름은 `@semachi/web`처럼 짓는다. 다른 패키지에서 `"@semachi/shared": "workspace:*"`로 가져다 쓴다 (B-8부터)

자주 쓰는 명령:

| 하고 싶은 것 | 명령 |
|---|---|
| 모든 패키지 검사·테스트·빌드 | 루트에서 `pnpm typecheck` / `pnpm test:run` / `pnpm build` (루트 `package.json`이 `pnpm -r`로 각 패키지에 넘김) |
| 패키지 하나만 | `pnpm --filter @semachi/web test:run` |
| 패키지 하나에 의존성 추가 | `pnpm --filter @semachi/server add express` |
| 웹 개발 서버 | `pnpm dev` |

- `-r`(recursive): 모든 패키지에서 실행. `--if-present`: 그 스크립트가 없는 패키지는 건너뜀 (서버엔 아직 테스트가 없다)
- 린트·포맷은 저장소 전체에 한 번 (루트 `.oxlintrc.json`·`.prettierrc.json`)

**검색 엔진 차단**: 검색 결과에서 빼려면 "읽게 두고 색인하지 말라고" 해야 한다.
- `<meta name="robots" content="noindex, nofollow">`(페이지), `X-Robots-Tag` 헤더(B-11, 서버 응답 전체)
- `robots.txt`의 `Disallow: /`는 "읽지 마"라서, 검색 엔진이 noindex 표시를 못 보고 주소만 결과에 남을 수 있다. 그래서 `robots.txt`는 열어 둔다

**실수하기 쉬운 곳**
- 폴더를 옮기면 설정 속 상대 경로가 깨질 수 있다. 이번엔 Vite·TS 설정이 웹 파일과 같이 옮겨져 그대로였고, `.gitignore`의 `!env/.env` 같은 경로는 고쳐야 했다
- 파일을 옮길 때는 `git mv`: 그냥 옮기면 git이 "지우고 새로 만듦"으로 볼 수 있어 기록을 따라가기 어렵다

## B-2 지금 서버 동작을 테스트로 고정 (2026-11-27)

**characterization test (현재 동작 고정 테스트)**: "맞는 동작"이 아니라 "지금 하는 동작"을 적은 테스트. 코드를 나누고(B-3) 버전을 올릴 때 동작이 바뀌지 않았는지 알려 준다. 이상한 동작도 일부러 그대로 적고 이름에 "현재 동작:"을 붙인다. 고칠 때(B-5~)는 그 테스트의 기대값을 함께 바꾼다
- 안 쓰면: 파일을 나누다 한 줄을 빠뜨려도 운영에 올리기 전까지 모른다. 이번에도 테스트를 처음 돌리자마자 B-1에서 넣은 `body-parser` 버전 때문에 JSON 요청이 모두 실패하는 것이 드러났다

**app과 main을 나누는 이유**: 테스트가 서버를 "켜지" 않고 앱만 가져다 요청을 보내려면, 앱 조립(`app.js`)과 실행(`main.js`: DB 연결·포트 열기·인증서)을 떼어 놓아야 한다. 웹에서 컴포넌트를 `main.tsx` 없이 렌더링해 테스트하는 것과 같다

**도구**
- **supertest**: Express 앱에 실제 포트를 열지 않고 HTTP 요청을 보낸다. `request(app).post('/team').send({...})` → 응답의 `status`·`body`·`headers`
- **mongodb-memory-server**: 테스트 동안만 진짜 MongoDB를 메모리에 띄운다. 실제 DB를 건드리지 않고, 테스트 파일마다 깨끗한 DB. 웹 테스트의 MSW(가짜 서버)와 달리 DB는 진짜라 조건(`$lt`·`$gte`) 같은 실제 동작까지 확인된다
- 시간: `vi.useFakeTimers({ toFake: ['Date'] })`로 "지금"만 고정한다. 타이머까지 가짜로 하면 DB 드라이버가 멈춘다

자주 쓰는 명령:

| 하고 싶은 것 | 명령 |
|---|---|
| 서버 테스트 | `pnpm --filter @semachi/server test:run` (watch: `test`) |
| 파일 하나 | `pnpm --filter @semachi/server exec vitest run test/teams.test.ts` |
| 테스트 하나 | 위 명령 뒤에 `-t "테스트 이름 일부"` |
| 서버 타입 검사 | `pnpm --filter @semachi/server typecheck` |

**배운 것**
- 같은 일을 하는 미들웨어를 두 번 쓰면(`bodyParser.json()` + `express.json()`) 버전 조합에 따라 깨진다. 1.x끼리는 "이미 읽음" 표시를 보고 건너뛰지만 2.x와 1.x는 서로의 표시를 모른다 → 버전 올리기(B-3)에서 하나만 남긴다
- "읽고 → 고치고 → 다시 쓰기"를 비동기로 하면 동시에 온 요청끼리 서로의 결과를 덮어쓴다(경쟁 상태). 지금 로그 파일이 그렇다(O1). 테스트에서도 앞 테스트의 덜 끝난 쓰기 때문에 가끔 실패했다
- 서버 시간대(D1): 서버는 보통 UTC다. `setHours(0,0,0,0)`의 "오늘 0시"는 서버 시간대 기준이라 한국 시각 오전 9시다. 그래서 날짜 계산은 시간대를 코드에 적어야 한다(B-5)
- 변형 검사(뮤테이션): 코드를 일부러 하나씩 망가뜨려 테스트가 잡는지 본다. 잡지 못하면 테스트가 그 부분을 보지 않는다는 뜻. 원본이 통과하는 것(기준선)을 먼저 확인하고, 망가뜨린 코드가 문법 오류면 "놓침"으로 잘못 셀 수 있다 (이번에 1건 그랬다)

**실수하기 쉬운 곳**
- 테스트가 `.env`(실제 비밀값)를 읽지 않게: 테스트용 값은 `vitest.config.mts`의 `env`에. `main.js`만 `.env`를 읽는다
- `insertOne`에 `undefined`를 넣으면 MongoDB에는 `null`로 들어간다. "필드 없음"을 만들려면 키를 빼야 한다 (`helpers.ts`의 `insert`가 뺀다)

## B-3 파일 나누기 + TypeScript + 최신 버전 (2026-11-27)

**서버 코드의 층** (웹의 `features`·`lib`처럼 역할로 나눔)
- `models/`: DB에 저장하는 모양 (Mongoose 스키마)
- `routes/`: 주소별로 요청을 받아 답하는 곳 (`router.get('/teams', ...)`)
- `middleware/`: 모든 요청이 라우트에 닿기 전에 거치는 처리 (CORS 헤더, 방문자 쿠키). `(req, res, next)`에서 `next()`를 불러야 다음으로 넘어간다
- `app.ts`(조립) / `main.ts`(실행) / `config.ts`(환경변수): 테스트는 `app.ts`만 쓰고, 실제 서버는 `main.ts`가 DB에 연결한 뒤 연다
- 의존성 넘기기: 라우터가 마스터 PIN·로그 함수를 직접 읽지 않고 인자로 받는다(`teamsRouter({ log, masterPin })`). 그래서 테스트가 환경변수를 건드리지 않고 원하는 값을 넣을 수 있다

**Node가 TypeScript를 바로 실행 (type stripping)**: Node 24는 `.ts` 파일에서 타입 부분만 지우고 실행한다. 빌드 단계가 없어 `node src/main.ts`로 끝
- 대신 규칙: 가져올 때 실제 확장자(`./app.ts`), 타입만 가져올 때는 `import type`, enum·namespace처럼 "지우기만 해서는 안 되는" 문법 금지 (`tsconfig.json`의 `erasableSyntaxOnly`가 막아 준다)
- 타입 검사는 따로: `pnpm --filter @semachi/server typecheck` (Node는 타입이 틀려도 그냥 실행한다)

**버전 올리기를 테스트로 확인하는 법**: 바뀔 만한 곳을 먼저 테스트로 고정하고(본문 없는 요청), 버전을 올린 뒤 깨진 테스트만 고친다. Express 5는 본문 없는 요청의 `req.body`를 `undefined`로 둬서 400이던 응답이 500이 됐다 → 테스트가 바로 잡았다

**health check**: `GET /health`는 "서버가 살아 있고 DB에 연결돼 있나"만 답하는 주소. 배포 뒤(B-11) 새 서버가 제대로 떴는지 자동으로 확인하는 데 쓴다. 안 쓰면: 서버 프로세스는 떠 있는데 DB가 끊긴 상태를 알 수 없다

**빨리 실패하기 (fail fast)**: 설정이 빠졌거나 DB에 연결하지 못하면 서버를 띄우지 않고 바로 끝낸다. 이전 서버는 떠 있으면서 요청마다 실패했다 → 배포가 "성공"으로 보여 문제를 늦게 안다

**종료 신호 (SIGTERM·SIGINT)**: Docker가 컨테이너를 멈출 때·Ctrl+C를 누를 때 프로그램에 보내는 신호. 받으면 새 요청을 그만 받고 하던 요청을 마친 뒤 끝낸다 (안 하면 저장 중이던 요청이 중간에 끊길 수 있다)

자주 쓰는 명령:

| 하고 싶은 것 | 명령 (저장소 루트) |
|---|---|
| 내 PC에서 서버 띄우기 (메모리 DB + 예시 데이터) | `pnpm dev:server:sample` → http://localhost:8081 (B-5 뒤 이름 바꿈: `dev:server`는 운영 DB) |
| 웹을 그 서버에 연결 | 다른 터미널에서 `pnpm dev:local` → http://localhost:3000 |
| 서버 살아 있나 | 브라우저에서 http://localhost:8081/health |
| 예시 데이터 처음으로 | 서버를 끄고 `pnpm --filter @semachi/server dev:sample:reset` |
| 웹을 운영 서버에 연결 (이전과 같음) | `pnpm dev` |

**실수하기 쉬운 곳**
- `pnpm dev`(운영 API)와 `pnpm dev:local`(내 PC 서버)을 헷갈리지 않기. `dev`로 켠 화면에서 지우면 진짜 데이터가 지워진다
- 개발 서버의 PIN은 개발용(마스터 `0000`, 예시 팀 `1234`)이다. 실제 PIN과 관계없다
- 휴대폰으로 개발 서버를 보려면 `apps/web/env/.env.localserver`의 `localhost`를 PC의 IP로 바꿔야 한다 (휴대폰에서 `localhost`는 휴대폰 자신)

## B-4 CI (GitHub Actions) (2026-11-27)

**CI (지속적 통합)**: 푸시할 때마다 GitHub의 컴퓨터가 저장소를 새로 받아 내 PC에서 하던 검사(린트·포맷·타입·테스트·빌드)를 똑같이 돌린다
- 왜: 내 PC에서 검사를 잊어도, 내 PC에만 있는 파일·설정 때문에 통과했어도 잡힌다. "깨끗한 컴퓨터에서도 통과한다"가 확인된다
- 안 쓰면: 깨진 코드가 `main`에 들어가고, B-11부터는 그대로 운영에 배포된다 (CD는 CI가 통과해야만 배포하게 만든다)

**워크플로 파일 읽는 법** (`.github/workflows/ci.yml`)
- `on`: 언제 도는지 (모든 브랜치 푸시, PR)
- `jobs.check`: 할 일 묶음 하나("검사"). `runs-on: ubuntu-latest` = GitHub가 빌려주는 리눅스 컴퓨터
- `steps`: 위에서부터 차례로. `uses:`는 남이 만든 액션(예: `actions/checkout` = 코드 받기), `run:`은 터미널 명령
- 한 단계가 실패하면 그 뒤 단계는 돌지 않고 빨간 X
- 캐시: 매번 받는 것(pnpm 패키지, MongoDB 실행 파일)을 저장해 두고 다음 실행에 다시 쓴다 → 빨라진다

**결과 보는 곳**
- 저장소 → **Actions** 탭 → 실행 하나 → "검사" → 단계별 로그 (실패한 단계는 빨간 X, 펼치면 오류)
- 커밋 옆의 ✓(통과)·✗(실패)·●(도는 중), PR 화면 아래와 **Checks** 탭

**리눅스에서만 깨지는 것**: 리눅스는 파일 이름 대소문자를 구분한다(`Teams.tsx` ≠ `teams.tsx`). 윈도우는 구분하지 않아 내 PC에서는 통과해도 CI에서 깨질 수 있다. 이름만 대소문자를 바꿀 때는 `git mv` 두 단계 (`docs/DIRECTORY_STRUCTURE.md` 규칙)

**브랜치 보호**: `main`·`dev`에 직접 푸시하지 못하게 하고, PR + CI 통과가 있어야 합치게 한다 (사전 결정 6의 흐름: 작업 브랜치 → PR → `dev` → PR → `main`)

자주 쓰는 명령:

| 하고 싶은 것 | 명령 |
|---|---|
| CI 돌리기 | 푸시하면 자동 (`git push origin api3.0`) |
| CI와 같은 검사를 내 PC에서 | `pnpm install --frozen-lockfile; pnpm lint; pnpm format:check; pnpm typecheck; pnpm test:run; pnpm build` |
| 내 PC 서버를 운영 DB에 | `pnpm dev:server` (+ `pnpm dev:local`) ⚠️ 실제 데이터가 바뀐다 (B-5 뒤 이름 바꿈) |

**실수하기 쉬운 곳**
- `--frozen-lockfile`: 잠금 파일(`pnpm-lock.yaml`)과 `package.json`이 맞지 않으면 설치를 멈춘다. 패키지를 추가했으면 잠금 파일도 함께 커밋한다
- 브랜치 보호의 "필수 검사"는 CI가 한 번 돌고 나야 목록에 "검사"가 나타난다
- Node 버전은 `.nvmrc` 한 곳에서 정한다 (CI가 읽는다). 내 PC의 Node도 같게 맞춘다

## B-5 보안·운영 수정 (2026-11-27)

**CORS (교차 출처 자원 공유)**: 브라우저는 A 주소의 웹이 B 주소의 서버 응답을 읽지 못하게 막는다. 서버가 "A는 괜찮다"는 헤더(`Access-Control-Allow-Origin: A`)를 보내야 읽게 해 준다
- 주소(출처) = `https://` + 도메인 + 포트. `semachi.net`과 `semachi.net:8081`은 다른 출처다
- 운영은 웹과 API가 같은 출처(`semachi.net`과 `semachi.net/api`)가 되므로 CORS가 필요 없다. 그래서 허락 목록(`CORS_ORIGINS`)은 개발(`localhost:3000`)·옮기는 동안의 옛 주소에만 쓴다
- 안 막으면: 다른 사이트가 사용자 브라우저를 통해 우리 서버를 부르고 응답을 읽을 수 있다

**SameSite 쿠키**: 쿠키를 "다른 사이트에서 온 요청"에도 보낼지. `None`=언제나, `Lax`=같은 사이트만(+ 링크로 들어올 때). 사이트 = 도메인 기준이라 포트가 달라도(`localhost:3000`→`:8081`) 같은 사이트다

**시도 횟수 제한 (rate limit)**: 일정 시간에 일정 횟수 이상이면 429(Too Many Requests)로 거절한다. 4자리 PIN은 1만 개뿐이라, 제한이 없으면 프로그램이 몇 분 만에 찾는다
- 무엇으로 셀지가 중요하다: 쿠키는 지우면 그만이라 IP로 센다. 그런데 학교 와이파이처럼 여럿이 IP 하나를 쓰면 서로 막히므로 "IP + 대상(팀)"으로도 센다
- 프록시(Caddy) 뒤에서는 서버가 보는 IP가 모두 Caddy의 IP다 → `TRUST_PROXY=1`로 "앞에 프록시 하나가 있으니 `X-Forwarded-For`의 IP를 믿어라"를 알려야 한다 (B-11). 안 하면 모든 사용자가 한 사람으로 세어진다

**보안 헤더 (helmet)**: 응답에 붙이는 "브라우저에게 주는 지시"들. 예: `X-Content-Type-Options: nosniff`(형식을 짐작하지 마라), `Strict-Transport-Security`(이 사이트는 HTTPS로만), `X-Frame-Options`(다른 사이트의 iframe에 넣지 마라)

**인덱스**: DB의 책갈피. `teamId` 인덱스가 있으면 "이 팀의 합주"를 찾을 때 전체를 훑지 않는다. 데이터를 바꾸지 않는다

**배운 것**
- 환경변수는 프로그램을 켤 때 한 번 읽힌다. `node --watch`는 코드가 바뀌면 서버를 다시 켜지만 환경변수는 처음 그대로다 → 개발 서버 스크립트를 고친 뒤에는 Ctrl+C로 끄고 다시 켠다 (이번에 켜 둔 서버가 새 CORS 설정 없이 돌아 웹을 막았다)
- 바꾸기 전에 위험한 경우를 먼저 테스트로 고정한다: "id 없이 삭제하면 아무것도 지우지 않는다"를 먼저 테스트로 만든 뒤 삭제 코드를 바꿨다
- 코드 주석의 주장도 확인한다: "Mongoose는 id 없이 지우면 첫 문서를 지울 수 있다"고 적었다가 확인해 보니 Mongoose 9는 아무것도 지우지 않았다 → 주석을 사실대로 고침

**실수하기 쉬운 곳**
- 개발 서버를 두 번 켜면 포트가 겹친다 → 이제 "이미 쓰고 있는 포트" 안내가 나온다. 켜 둔 터미널을 찾아 Ctrl+C
- PIN 시도 제한은 서버 메모리에 있다. 개발 중에 많이 틀려 막혔으면 개발 서버를 다시 켜면 풀린다 (운영은 15분 기다림)

**(B-5 뒤) `querySrv ECONNREFUSED`**: Atlas 주소(`mongodb+srv://…mongodb.net`)는 DNS에 "이 클러스터의 실제 DB 서버들"을 물어본(SRV 조회) 뒤 접속한다. 이 오류는 DB가 아니라 그 DNS 조회가 막혔다는 뜻이다. 이 PC의 Node가 응답 없는 DNS(127.0.0.1)를 쓰고 있었다 → `DNS_SERVERS`로 공용 DNS를 정하면 된다 (`pnpm dev:server`는 알아서 한다). 확인 명령: `nslookup -type=SRV _mongodb._tcp.<클러스터 주소>`

## B-6 PIN (2026-11-27)

**클라이언트 확인 vs 서버 확인**: 지금까지는 웹이 "PIN 맞아?"를 물어본 뒤, 맞으면 "지워 줘"를 따로 보냈다. 서버는 "지워 줘"만 받으면 그냥 지웠다 → 웹을 거치지 않고 요청을 직접 보내면 누구나 지울 수 있었다 (B1). 규칙: **바꾸는 요청을 받는 쪽(서버)이 직접 확인한다**. 웹의 확인은 "빨리 알려 주기"용일 뿐이다

**해시**: 되돌릴 수 없게 바꾼 값. 저장된 해시와, 넣은 PIN을 같은 방법으로 바꾼 값을 비교한다. 소금(salt): PIN마다 다른 무작위 값을 섞어 같은 PIN도 다른 해시가 되게
- 한계: 4자리 PIN은 1만 개뿐이라 DB가 통째로 새면 시간을 들여 풀 수 있다. 해시는 "DB 화면·백업에서 PIN이 그대로 보이지 않게" 하는 정도이고, 진짜 보호는 서버의 시도 횟수 제한이다
- 전환: 옛 서버(평문 비교)와 같은 DB를 쓰는 동안은 평문으로 두고, 운영 전환 때 한 번에 바꾼다 (`scripts/hash-pins.ts`). 새 서버는 그 사이 평문·해시를 둘 다 읽는다 → 언제 바꿔도 깨지지 않는다

**`select: false`**: DB에는 있지만 조회 결과에 기본으로 넣지 않는 필드. PIN이 필요한 곳만 `.select('+pin')`. 목록 응답에 실수로 PIN이 섞일 일이 없어진다

**응답 헤더로 덧붙이기**: 본문(true/false)은 그대로 두고 "몇 번 틀렸는지"는 헤더(`Pin-Attempts`)로 보냈다. 응답 모양을 바꾸지 않아 기존 코드가 깨지지 않는다. 다른 주소에서 부르는 웹(개발)은 서버가 `Access-Control-Expose-Headers`에 적은 헤더만 읽을 수 있다

**마스터 PIN을 DB로**: 환경변수는 바꾸려면 서버에 들어가 파일을 고치고 다시 켜야 한다. DB에 두면 관리자 화면에서 바꿀 수 있고, 같은 DB를 보는 서버(운영·베타)가 바로 따른다. 처음(DB에 없을 때)은 환경변수 값

**실수하기 쉬운 곳**
- `pnpm dev:server`(운영 DB)를 켜 둔 채 서버 코드를 고치면 `node --watch`가 새 코드로 다시 켠다 → 새 코드가 운영 DB에 바로 닿는다. 큰 서버 작업 중에는 끄거나 `dev:server:sample`로
- 해시로 바꾸는 스크립트는 되돌릴 수 없다. 백업 → 세어 보기 → `--apply` 순서. 옛 서버가 아직 돌고 있으면 실행하지 않는다

**(B-6 뒤) 시도 제한 설계 다시 짜기**: "한 번 맞추면 틀린 횟수를 지운다"는 편하지만, 공격자가 자기가 아는 PIN(새로 만든 팀)으로 언제든 지울 수 있으면 제한이 사라진다. 그래서
- 지우는 범위를 좁힌다: 맞춘 그 대상(팀)의 횟수만. 다른 팀의 PIN을 찾는 데는 도움이 안 된다
- 모든 대상에서 통하는 열쇠(마스터 PIN)가 있으면, 대상별로 지우는 것만으로는 막을 수 없다 → 지워지지 않는 IP 전체 횟수를 하나 더 둔다
- 라이브러리가 맞지 않으면 작게 직접 만든다: express-rate-limit은 요청이 라우트에 닿기 전에 센다. "합주를 DB에서 읽고 나서 그 팀으로 센다"는 핸들러 안에서만 할 수 있어 `lib/pin-guard.ts`를 만들었다 (메모리의 Map 하나, 50줄 남짓)
- 메모리에 두면: 서버를 다시 켜면 처음부터, 서버가 여러 대면 각자 센다. 이 서비스 크기에는 충분하다 (커지면 Redis 같은 공용 저장소)

## B-7 활동 기록·관리자 화면 (2026-11-27)

**로그 두 가지**
- **운영 로그**: "서버가 잘 돌고 있나" (요청·오류·걸린 시간). 표준 출력에 JSON 한 줄씩(pino) → Docker가 모아 둔다(`docker logs`). 문제를 찾을 때 보고 며칠 뒤 버린다
- **활동 기록(감사 로그)**: "누가 무엇을 했나". 오래 두고 찾아봐야 해서 DB(`activities`)에. 관리자만 본다
- 왜 나누나: 목적·보관 기간·보는 사람이 다르다. 예전 `log.txt`는 둘이 섞였고, 파일을 통째로 다시 쓰는 방식이라 동시에 오면 줄이 사라졌다

**TTL 인덱스**: "이 날짜 필드에서 N초가 지난 문서는 MongoDB가 알아서 지워라"는 인덱스. 1년 지난 활동 기록을 지우는 작업을 따로 만들 필요가 없다

**JSON 구조화 로그**: `{"level":30,"req":{"method":"GET","url":"/teams"},"res":{"statusCode":200},"responseTime":4}` 처럼 한 줄이 객체라 검색·집계가 쉽다. 로그에 무엇을 넣지 않을지가 중요하다: 본문(PIN), 쿠키(방문자 id)는 넣지 않았다

**세션 쿠키와 서명**: 로그인했다는 표시를 브라우저 쿠키에 둔다. 사용자가 쿠키 값을 고칠 수 있으니 서버만 아는 비밀로 서명(HMAC)해, 서명이 맞을 때만 믿는다. `HttpOnly`(자바스크립트로 못 읽음), `Secure`(HTTPS만), `SameSite=Strict`(다른 사이트에서 오는 요청엔 안 보냄)로 훔치거나 남용하기 어렵게

**처음부터 모으는 정보 줄이기**: 사람을 짐작할 수 있는 정보(IP·기기)는 꼭 필요한 만큼만, 보관 기간을 정하고, 볼 수 있는 사람을 좁히고, 모은다는 사실을 알린다 (푸터 한 줄)

**지연 불러오기 (lazy import)**: `/admin`일 때만 관리자 화면 코드를 내려받는다 (`React.lazy`). 보통 방문자는 그 코드를 받지 않는다

자주 쓰는 것:

| 하고 싶은 것 | 방법 |
|---|---|
| 관리자 화면 | 웹 주소 뒤에 `/admin` (내 PC: http://localhost:3000/admin), 마스터 PIN |
| 누가 이 팀을 바꿨나 | 관리자 → 활동 기록 → 동작 "팀" → 그 줄의 "자세히" |
| 이 사람이 다른 방문자 id도 쓰나 | 방문자 id를 눌러 "같은 IP·기기의 다른 방문자" |
| 운영 로그 보기 (B-11 뒤 서버에서) | `docker compose logs api --since 1h` |

**실수하기 쉬운 곳**
- "같은 IP"는 같은 사람이라는 뜻이 아니다: 학교 와이파이·통신사 공유 IP는 여러 사람이 함께 쓴다. "같은 기기"(User-Agent)도 같은 기종·같은 버전이면 겹친다. 단서일 뿐, 단정하지 않는다
- 관리자 쿠키는 서버를 다시 켜면 풀린다 (비밀을 켤 때마다 새로 만든다). 배포 뒤 다시 로그인

## B-8 입력 검증·데이터 정리 (2026-11-28)

**입력 검증 (validation)**: 서버가 받은 요청이 약속한 모양인지 저장하기 전에 확인한다. 아니면 400(Bad Request, "요청이 잘못됐다")
- 왜: 웹 입력칸의 `maxLength`·버튼 막기는 웹을 거칠 때만 통한다. 요청은 누구나 직접 보낼 수 있으므로(B1과 같은 이유) 서버가 다시 본다
- 안 하면: 범위 밖 시간칸·빈 팀명·10,000자 글이 그대로 저장된다. 이상한 데이터 한 건이 화면을 깨뜨릴 수 있다 (실제로 `endTime: null` 합주 1건이 있었다, ISSUES P9)
- 400 vs 404 vs 403 vs 500: 400 = 요청 모양이 틀림, 404 = 요청은 맞지만 대상이 없음, 403 = 권한(PIN)이 없음, 500 = 서버가 처리하다 실패(서버 쪽 버그). 잘못된 id로 500이 나던 것은 "사용자 실수를 서버 고장으로 보고"하던 셈이다

**스키마 공유 (packages/shared)**: 웹과 서버가 같은 Zod 스키마 파일을 쓴다
- 길이 제한(`limits.ts`)을 한곳에 두면 웹 입력칸과 서버 검사가 저절로 같아진다. 따로 적으면 언젠가 어긋난다 (웹은 30자 되는데 서버는 20자에서 거절 → "저장하지 못했어요")
- 응답 스키마도 공유해서, 서버 테스트(`contract.test.ts`)가 "서버가 만든 데이터를 웹이 읽을 수 있는지"를 확인한다. 웹은 맞지 않는 항목을 화면에서 빼므로, 깨지면 "만들었는데 안 보이는" 버그가 된다
- Zod가 해 주는 것: 검사 + 정리(앞뒤 공백 빼기, 정의하지 않은 필드 버리기) + TypeScript 타입(`z.infer`). 검사를 통과한 값만 쓰면 `req.body`의 아무 값(any)을 저장하지 않게 된다

**검사 순서**: id 형식 → 대상이 있나(404) → 본문 → PIN
- 본문이 틀리면 PIN을 보지 않는다: 어차피 저장하지 않을 요청으로 틀린 횟수가 늘지 않게
- 대상이 없으면 본문과 관계없이 404: 웹이 "이미 삭제됐어요"를 보여 주는 기준이 404라서
- 400 응답에 "어느 칸이 왜"(path·message)만 담고 받은 값은 담지 않는다 (PIN이 섞여 있을 수 있다)

**시간대**: 서버 컴퓨터의 시계는 보통 UTC다. "오늘"을 서버 시간대로 계산하면(`setHours(0,0,0,0)`) 한국의 오늘과 9시간 어긋난다
- 날짜 계산은 기준 시간대를 코드에 적는다 (`lib/time.ts`). 한국은 서머타임이 없어 늘 UTC+9라 9시간을 더하고 빼서 계산한다 (서머타임이 있는 나라면 시간대 라이브러리가 필요하다)
- 테스트는 서버 시간대를 UTC로 두고, 여러 TZ에서 같은 답이 나오는지 본다 (`process.env.TZ`를 바꿔 가며)
- 저장 모양: 날짜만 의미 있는 값(`due` 'YYYY-MM-DD')은 그날 UTC 0시로 저장된다. 비교할 때는 "한국 날짜의 0시"(= 전날 15:00Z)와 비교한다

**파생 필드 (derived field)**: 다른 값에서 계산되는 값 (`day` = nextDate의 요일, `teamName` = 팀의 이름)
- 클라이언트가 보낸 파생 값을 그대로 저장하면 원래 값과 어긋날 수 있다 → 서버가 직접 계산해 채운다
- 남길지 지울지: 읽는 쪽이 있으면 남긴다(옛 웹이 `day`·`teamName`을 읽는다). 아무도 안 읽으면 지운다(`type`). "누가 이 필드를 읽나"를 옛 코드(`git show main:…`)에서 확인하고 정했다

**같은 DB를 쓰는 동안 필드를 바꾸는 법** (사전 결정 10): ① 새 코드가 그 필드를 쓰지 않게 → ② 읽는 쪽이 없는지 확인 → ③ 운영 전환 때 저장된 값을 스크립트로 지움. 스크립트는 "세어 보기 → 백업 → `--apply` → 다시 세어 보기"

자주 쓰는 것:

| 하고 싶은 것 | 방법 |
|---|---|
| 서버가 어떤 칸을 거절했는지 | 400 응답 본문의 `issues` (브라우저 개발자 도구 → Network → 그 요청 → Response) |
| 길이 제한 바꾸기 | `packages/shared/src/limits.ts` 한 곳 (웹·서버가 함께 바뀐다) |
| 공유 패키지만 검사·테스트 | `pnpm --filter @semachi/shared typecheck` / `test:run` |
| 합주 type 지우기 (B-14) | `node --env-file=<.env> scripts/remove-ensemble-type.ts` → 확인 → `--apply` |

**실수하기 쉬운 곳**
- 서버 테스트를 새 PC에서 처음 돌리면 테스트 파일들이 동시에 MongoDB 실행 파일(약 100MB)을 받으려다 "Cannot unlock file" 오류가 날 수 있다 → 파일 하나로 먼저 받는다: `pnpm --filter @semachi/server exec vitest run test/health.test.ts`
- 셸마다 Node 버전이 다를 수 있다 (fnm·nvm은 셸을 켤 때 PATH를 바꾼다). `node -v`가 `.nvmrc`(26)와 다르면 `fnm use` 또는 새 터미널. 이 PC의 기본 Node 22.14는 `.ts`를 바로 실행하는 기능(type stripping)이 기본으로 켜져 있지 않아 서버가 돌지 않는다
- 응답 스키마에서 필드를 지우면 "와도 버린다"(Zod 기본)이지 "오면 실패"가 아니다. 옛 데이터에 남은 `type`·`pin`이 와도 화면은 깨지지 않는다

## B-9 팀 자동 삭제·정리 작업 (2026-11-28)

**예약 작업 (scheduled job)**: 요청이 없어도 서버가 정해진 시각에 스스로 하는 일. 여기서는 "매일 04:00에 날짜 지난 팀·합주 지우기"
- 방법 여러 가지: ① 서버 안의 타이머(`setTimeout`, 이번 방식) ② 서버 컴퓨터의 cron(리눅스의 예약 실행) ③ 별도 작업 서버. 이 서비스는 서버 하나라 ①이 가장 단순하다. 서버가 꺼져 있던 시간의 일은 다음에 켤 때 한다("시작할 때 한 번")
- `setInterval(24시간)` 대신 매번 "다음 04:00까지 남은 시간"을 다시 계산한다: 실행에 걸린 시간만큼 조금씩 밀리지 않게
- `timer.unref()`: 이 타이머 하나 때문에 프로그램이 끝나지 못하는 일이 없게 (종료 신호를 받으면 바로 끝난다)
- 실패해도 서버는 계속 돌고 다음 날 다시 한다 (운영 로그에 오류)

**여러 서버가 같은 DB를 쓸 때의 예약 작업**: 운영·베타가 같은 DB라, 둘 다 돌면 같은 일을 두 번 한다. 그래서 환경변수(`CLEANUP_ENABLED`)로 운영 하나에서만 켠다. **기본값은 꺼짐**이 안전하다: 켜는 것을 잊으면 정리가 늦어질 뿐이지만, 끄는 것을 잊으면(내 PC에서 운영 DB에 연결한 서버 등) 운영 데이터가 지워진다

**숨기기 vs 지우기**: 지난 합주는 지금까지 목록 API가 숨기기만 하고 DB에 남았다. 정리 작업은 "목록이 숨기는 것과 똑같은 기준"으로 지운다 → 지우기 전후 화면이 같다 (테스트가 이것을 직접 비교한다). 기준이 다르면 화면에 보이던 것이 사라지거나, 숨겨진 것이 계속 쌓인다

**지우기 전에 세어 보기**: 처음 켜면 그동안 숨겨져 있던 지난 합주가 한꺼번에 지워진다. 그래서 첫 실행 전에 `scripts/cleanup.ts`(세어 보기)로 무엇이 지워질지 본다. 지운 것은 활동 기록에 전체 내용으로 남아, 지워진 뒤에도 무엇이었는지 알 수 있다

**타이머 테스트**: `vi.useFakeTimers()`로 시계를 가짜로 하고 `vi.advanceTimersByTimeAsync(16시간)`처럼 시간을 앞으로 감는다. 진짜로 16시간을 기다리지 않는다. 단, DB를 쓰는 테스트에서 타이머까지 가짜로 하면 DB 드라이버가 멈추므로(B-2) 예약 테스트는 DB 없이 가짜 `run`으로 한다

자주 쓰는 것:

| 하고 싶은 것 | 방법 |
|---|---|
| 지금 무엇이 지워질지 보기 | `node --env-file=<.env> scripts/cleanup.ts` (서버 폴더에서) |
| 정리 작업 켜기 (운영만) | 서버 환경변수 `CLEANUP_ENABLED=true` → 시작 로그에 "정리 작업: 켜짐 (매일 04:00)" |
| 무엇이 자동으로 지워졌나 | 관리자 → 활동 기록 → "팀 자동 삭제"·"합주 자동 삭제" → 자세히 |

**실수하기 쉬운 곳**
- 팀 자동 삭제 날짜가 "오늘"이면 오늘 하루는 남고 다음 날 04:00에 지워진다 ("이 날짜 이후에 자동으로 삭제돼요"). 합주의 반복 종료 날짜와 같다
- 베타에서는 정리 작업이 돌지 않는다. 베타에서 자동 삭제를 시험하려면 세어 보기 스크립트로 잡히는지 본다

## B-10 API 형태 정리 (2026-11-28)

**REST 주소 규칙**: "무엇(리소스)"은 주소로, "어떻게(동작)"는 메서드로 나타낸다
- 모음은 복수형 `/teams`, 하나는 `/teams/:id`. `GET` 읽기, `POST` 만들기, `PUT` 고치기, `DELETE` 지우기
- id를 `?id=`(쿼리)가 아니라 주소 안에: 쿼리는 "목록을 거르는 조건"(예: `/admin/activities?visitorId=…`)에 쓰고, "어느 것"은 주소의 일부로 쓰는 것이 관례다
- 동사가 꼭 필요한 동작은 그 대상 아래에: `POST /teams/:id/check-pin`
- 이점: 주소만 보고 무엇을 하는지 알 수 있고, 같은 대상의 읽기·고치기·지우기가 같은 주소라 일관된다

**상태 코드로 결과 알리기**: 200 OK(읽기·수정), 201 Created(새로 만듦), 204 No Content(성공, 돌려줄 본문 없음 — 삭제), 400·401·403·404·429(요청 쪽 문제), 500(서버 쪽 문제)
- 클라이언트(웹)는 본문을 열어 보지 않고 상태 코드만으로 처리를 나눌 수 있다 (웹은 지금 404·403·429만 본다)

**오류 응답을 한 모양으로**: `{ error: { code, message, issues? } }`
- `code`: 프로그램이 읽는 값 (바뀌지 않는다). `message`: 사람이 읽는 설명 (바뀔 수 있다 → 테스트·웹은 code로 비교)
- 모양이 제각각이면(`{ id: -1 }`·`false`·HTML) 받는 쪽이 경우마다 따로 처리해야 한다

**오류 처리 미들웨어**: Express는 `(err, req, res, next)` 인자 넷짜리 미들웨어를 "오류 처리기"로 본다. 라우트에서 오류가 던져지면 그 뒤 일반 미들웨어를 건너뛰고 여기로 온다
- Express 5부터는 async 핸들러의 오류(거부된 Promise)도 자동으로 넘어온다 → 라우트마다 `try { … } catch { res.status(500) }`를 쓰지 않아도 된다
- 맨 뒤에 둔다: 라우트들 → `notFound`(아무도 답하지 않음) → `errorHandler`
- 오류 내용(스택·DB 메시지)은 응답에 넣지 않는다: 공격자에게 내부 구조를 알려 준다. 운영 로그에만

**API를 바꿀 때 옛 클라이언트**: 주소·요청 모양을 바꾸면 옛 클라이언트는 깨진다. 이 서비스는 웹과 서버를 한 번에 바꾸므로(모노레포·같은 배포) 괜찮지만, 이미 배포된 옛 웹(브라우저에 열려 있는 탭)은 새 서버와 맞지 않는다 → 운영 전환 때 웹과 서버를 함께 바꾸고, 옛 탭은 새로 고침

**큰 이름 바꾸기를 안전하게**: 테스트 수백 개의 주소를 손으로 고치지 않고 한 번 쓰는 스크립트(정규식)로 바꾼 뒤, 테스트를 돌려 실패한 것만 보며 고쳤다. 테스트가 있으니 "빠뜨린 곳"이 실패로 드러난다

자주 쓰는 것:

| 하고 싶은 것 | 방법 |
|---|---|
| 서버가 왜 거절했나 | 응답 본문의 `error.code` (+ 400이면 `error.issues`) |
| 오류 코드 목록 | `packages/shared/src/response.ts`의 `API_ERROR_CODES` |
| 새 오류 응답 | 서버 `sendError(res, 'NOT_FOUND', { message: '…' })` (상태 코드는 코드로 정해짐) |

**실수하기 쉬운 곳**
- 라우트 순서: `/notices/check-pin`을 `/notices/:id`보다 먼저 등록해야 한다. 아니면 `check-pin`을 id로 읽는다 (여기서는 메서드가 POST·GET으로 달라 겹치지 않지만, 같은 메서드면 문제가 된다)
- 204에는 본문을 보내지 않는다 (`res.status(204).end()`). 보내도 브라우저가 버린다

## B-11 배포 준비물 (2026-11-28)

**Docker 이미지·컨테이너**: 이미지는 "프로그램 + 실행에 필요한 것 전부(Node, 패키지, 코드)"를 묶은 파일, 컨테이너는 그 이미지를 실행한 것
- 왜: 서버에 Node·pnpm을 설치하고 버전을 맞출 필요가 없다. CI에서 확인한 그 이미지가 그대로 서버에서 돈다. 되돌리기는 이전 이미지 이름으로 다시 켜기
- 안 쓰면: 서버에서 `git pull` → `pnpm install` → 재시작을 손으로 (지금의 `api.js` 방식). 서버마다 환경이 조금씩 달라지고, 실패하면 반쯤 바뀐 상태가 남는다

**Dockerfile 읽는 법**: 위에서부터 한 줄이 한 "층(layer)". 바뀌지 않은 층은 캐시를 그대로 쓴다
- 그래서 `package.json`·잠금 파일을 먼저 복사하고 설치한 뒤에 소스를 복사한다: 소스만 고치면 설치 층은 다시 돌지 않는다
- **multi-stage**: `FROM … AS deps`(설치용)와 마지막 `FROM`(실행용)을 나눈다. 실행 이미지에는 결과만 복사해 pnpm·캐시·개발 도구가 들어가지 않는다 (작고 안전)
- **ARM·x86**: 서버 CPU를 아직 모른다. `--platform=$BUILDPLATFORM`을 붙인 단계는 만드는 컴퓨터(GitHub, x86)에서 돌고, 결과(JS 파일)는 CPU와 관계없어 ARM 이미지에도 그대로 쓴다. 마지막 단계는 복사만이라 느린 에뮬레이션(QEMU)이 거의 필요 없다
- `.dockerignore`: 이미지를 만들 때 보내지 않을 파일. 루트 `.env`(비밀값)·`node_modules`를 꼭 뺀다

**docker compose**: 컨테이너 여러 개(caddy·api·web·베타 둘·백업 도구)를 `compose.yaml` 하나로 켜고 끈다
- `profiles`: 이름을 붙인 서비스는 `docker compose up -d`만으로는 켜지지 않는다. 아직 배포하지 않은 쪽을 실수로 켜지 않게
- `healthcheck`: "떠 있다"가 아니라 "제대로 답한다"(GET /health)를 컨테이너 상태로. `up --wait`가 healthy까지 기다린다
- `env_file`: 비밀값은 compose.yaml(저장소)에 쓰지 않고 서버의 파일에서 읽는다. 값에 `$`가 있으면 작은따옴표 (아니면 변수로 읽힌다)
- 컨테이너끼리는 서비스 이름이 주소다 (`api:8081`). 바깥에는 caddy의 80·443만 연다

**리버스 프록시 (Caddy)**: 바깥 요청을 받아 안쪽 서버에 나눠 주는 서버
- 주소로 나누기: `semachi.net/api/*` → api, 그 밖 → web. 웹과 API가 같은 주소라 CORS가 필요 없다 (S3)
- HTTPS: Caddy가 Let's Encrypt 인증서를 알아서 받고 갱신한다 (O3. 지금 `api.js`는 인증서 파일을 직접 읽어 갱신 뒤 재시작이 필요했다). 그래서 80·443이 Caddy에게 열려 있어야 한다
- 프록시 뒤의 서버는 요청을 보낸 곳이 Caddy로 보인다 → Caddy가 진짜 IP를 `X-Forwarded-For`에 넣고, Express는 `TRUST_PROXY=1`(앞에 프록시 하나)로 그 값을 믿는다. 잘못 정하면 모두 한 IP로 세어 PIN 시도 제한에 서로 걸린다
- 기본 인증(basic auth): 베타 주소를 처음 열 때 브라우저가 아이디·암호를 묻는다. 암호는 해시로만 저장

**SPA 주소**: `/admin` 같은 화면 주소에는 실제 파일이 없다 → 파일이 없으면 `index.html`을 주고 웹(React)이 주소를 보고 그린다 (`try_files {path} /index.html`). 단 `/assets/*`는 없으면 404 (지난 파일을 HTML로 받으면 화면이 깨진다)

**캐시**: Vite가 만든 `/assets/*` 이름에는 내용 해시가 붙는다(`index-DIYr.js`) → 1년 캐시해도 된다 (내용이 바뀌면 이름이 바뀜). `index.html`은 `no-cache` → 배포하면 바로 새 화면

**CD (자동 배포) 흐름**: 푸시 → 검사 → 이미지 만들기 → GHCR(GitHub의 이미지 저장소)에 올리기 → SSH로 서버에서 `deploy.sh`
- **재사용 워크플로**(`workflow_call`): deploy.yml이 ci.yml을 그대로 불러 검사한다. 검사 단계를 두 번 적지 않는다
- **Environments**: 배포 대상(beta·production)마다 Secrets·승인·배포 기록을 따로. production 비밀값은 `main` 배포에서만 읽힌다
- **Secrets vs Variables**: Secrets는 비밀(로그에 `***`로 가려짐), Variables는 공개 설정(`DEPLOY_BETA=true` 같은 스위치)
- 배포용 SSH 키는 따로 만든다: 문제가 생기면 그 키만 지우면 된다. `known_hosts`로 접속할 서버가 진짜인지 확인
- GHCR에서 받을 때 서버는 그 실행의 임시 토큰(`GITHUB_TOKEN`)을 잠깐 쓰고 로그아웃 → 서버에 오래 남는 토큰이 없다
- 되돌리기: 잘 되던 때의 실행을 다시 돌리면(Re-run) 그때 이미지로 다시 켠다. 이미지 이름에 커밋을 붙인 이유

**서버 없이 배포물 확인하기**: CI 안에서 실제 배포와 같은 compose.yaml을 빈 MongoDB와 함께 띄우고 `curl`로 확인한다 (`deploy/smoke/run.sh`). 서버에 처음 올릴 때 "설정 오타로 안 뜸" 같은 문제를 미리 잡는다

자주 쓰는 것 (서버, `/srv/semachi`에서):

| 하고 싶은 것 | 명령 |
|---|---|
| 상태 | `docker compose ps` |
| 로그 | `docker compose logs --tail 100 -f api` |
| 다시 켜기 | `docker compose restart api` |
| 백업 | `bash backup.sh` |
| 스크립트 | `docker compose run --rm --no-deps api node scripts/cleanup.ts` |
| 손으로 배포 | `bash deploy.sh <beta\|production> <api 이미지> <web 이미지>` |

**실수하기 쉬운 곳**
- 파일 하나를 컨테이너에 연결(bind mount)하면, 그 파일을 새 파일로 바꿔 쓸 때 컨테이너는 옛 파일을 계속 본다 → Caddyfile은 폴더(`caddy/`)째 연결했다
- env 파일을 바꾸면 컨테이너를 다시 만들어야 읽는다 (`docker compose up -d <서비스>`, restart로는 안 됨)
- Caddy 설정에 빈 값(`BETA_AUTH_HASH`)이 있으면 Caddy 전체가 뜨지 않는다 → 운영도 멈춘다. 바꾼 뒤 `docker compose logs caddy`
- Let's Encrypt는 같은 주소로 너무 자주 실패하면 잠시 막는다: `caddy_data` 볼륨(받은 인증서)을 지우지 않는다
- 정리 작업(`CLEANUP_ENABLED=true`)은 운영 api가 **켜질 때** 바로 한 번 돈다 → 운영을 처음 켜기 전에 `cleanup.ts`로 세어 보고 확인
