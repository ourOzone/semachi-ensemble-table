## 🔒 보안

### S1. `GET /` 활동 로그 공개 + 저장형 XSS 🔴
- **현재:** `GET /`가 `log.txt` 전체를 `<br>`로 이어 붙여 HTML로 응답합니다. 로그에는 사용자 입력(한마디 본문, 팀 이름)이 그대로 들어갑니다 (`addnote_${data.text}`).
- **문제:**
  - 한마디에 `<img src=x onerror="...">`를 쓰면, 이후 `/`를 연 사람의 브라우저에서 스크립트가 실행됩니다. 이 스크립트는 API와 같은 origin에서 실행되므로 API를 마음대로 호출할 수 있습니다.
  - 인증이 없어, 방문자 ID와 활동 내역을 누구나 볼 수 있습니다.
- **제안:** 엔드포인트를 삭제하거나, 관리자 인증을 붙이고 `Content-Type: text/plain`으로 응답합니다.

### S2. PIN 무차별 대입 🔴
- **현재:** `check-team-pin`·`check-note-pin`·`check-notice-pin`에 시도 횟수 제한이 없습니다. 4자리 PIN은 10,000가지뿐입니다.
- **특히 위험한 곳:** `check-notice-pin`은 마스터 PIN과만 비교해 `true/false`를 돌려줍니다. 마스터 PIN이 짧다면 이 API로 찾아낼 수 있고, 마스터 PIN은 모든 팀·한마디의 PIN을 대신합니다.
- **제안:**
  - `express-rate-limit`으로 IP와 방문자 쿠키 기준의 시도 횟수를 제한합니다 (예: 분당 10회).
  - 실패가 쌓이면 일정 시간 잠급니다.
  - 마스터 PIN은 길고 무작위인 값으로 바꿉니다.

### S3. CORS 전체 허용 🔴
- **현재:** 요청의 `Origin`을 그대로 `Access-Control-Allow-Origin`에 넣고 `Allow-Credentials: true`를 붙입니다.
- **문제:** 어떤 사이트든 방문자의 브라우저로 API를 쿠키와 함께 호출하고 응답을 읽을 수 있습니다. 변경 API에 인증이 없어서(B1) 다른 사이트에서 삭제 요청도 보낼 수 있습니다.
- **제안:** 허용할 Origin 목록을 둡니다: 운영 도메인과 개발 서버 `http://localhost:5173`.

### S4. PIN 평문 저장 🟡
- **현재:** 팀·한마디의 `pin`을 DB에 평문으로 저장하고, `===`로 비교합니다.
- **제안:**
  - `bcrypt`나 `argon2`로 해시해 저장합니다. 비교는 `compare`를 쓰고, 마스터 PIN 비교에는 `crypto.timingSafeEqual`을 씁니다.
  - 스키마에서 `pin: { type: String, select: false }`로 두면 B3(PIN 노출)도 함께 막힙니다.

### S5. 입력값 검증 없음 🟡
- **현재:** mongoose 스키마에 `required`, `min`, `max`, `maxlength`가 없고, 요청 본문을 그대로 저장합니다.
- **생길 수 있는 데이터:**
  - `startTime > endTime`, 범위를 벗어난 시간 칸(0~29), 범위를 벗어난 요일(0~6)
  - 길이 제한이 없는 한마디·공지·팀 이름, 길이가 7이 아닌 `desc`
- **잘못된 ID:** ID 형식이 틀리면(`/team/abc`) CastError로 500이 납니다. 400이나 404가 맞습니다.
- **제안:**
  - 라우트 앞에서 Zod로 검증합니다. 프론트가 이미 Zod 스키마(`src/types/response.ts`)를 쓰고 있어 공유할 수 있습니다.
  - 또는 mongoose validator를 추가합니다.
  - ID 형식은 `mongoose.isValidObjectId()`로 미리 검사합니다.

## 📅 데이터 · 도메인

### D1. 시간대 가정 불일치 🟡 (확인 필요)
- **현재:** 코드 안의 두 곳이 서로 다른 시간대를 가정합니다.
  - `getTime()`(로그 시각)은 서버 시계가 UTC라고 보고 +9시간을 더합니다.
  - `GET /ensembles`의 `today.setHours(0, 0, 0, 0)`은 서버의 **로컬** 자정을 기준으로 합니다.
- **결과:** 서버의 시간대에 따라 둘 중 하나는 지금 틀려 있습니다.
  - 서버가 UTC라면: 오늘 기준이 KST 오전 9시가 됩니다. 일회성 합주의 `nextDate`가 KST 0~9시 사이 시각으로 저장돼 있으면, **합주 당일 오전 9시부터 목록에서 빠집니다.**
  - 서버가 KST라면: 로그 시각이 9시간 밀립니다.
- **제안:**
  - 서버 `TZ`를 먼저 확인합니다.
  - 날짜만 의미가 있는 값(`nextDate`)은 `'YYYY-MM-DD'` 문자열로 저장합니다.
  - 기준 시간대(`Asia/Seoul`)를 코드에 명시합니다.
  - 프론트도 3단계에서 날짜에 시각이 붙는 문제를 고칩니다. 저장 형식이 바뀌면 함께 맞춥니다.

### D2. 반복 합주의 "다음 날짜"를 클라이언트가 계산 🟡
- **현재:** 반복 합주의 `nextDate`는 지난 날짜로 DB에 남습니다. 클라이언트가 불러올 때마다 "오늘 이후 가장 가까운 같은 요일"을 다시 계산합니다. "다음 번에 안 해요"(미루기)는 클라이언트가 `nextDate`를 +7일 해서 `PUT`으로 덮어씁니다.
- **문제:**
  - 계산 규칙이 클라이언트마다 따로 있습니다. 앱을 새로 만들거나 다른 클라이언트가 생기면 규칙이 갈라집니다.
  - 미루기가 일반 수정 API를 거쳐, 다른 필드까지 통째로 다시 씁니다.
- **제안:** 서버가 다음 날짜를 계산해 응답에 넣습니다. 더 나아가면 이렇게 저장합니다.
  - "반복 규칙(요일·시작일·시간) + 건너뛸 날짜 목록(`skipDates`)"
  - 미루기는 `POST /ensembles/:id/skip` (해당 날짜를 `skipDates`에 추가)
  - 지난 일회성 합주의 정리도 서버의 한 곳에서 처리됩니다.

### D3. 합주의 레거시·중복 필드 🟡
- **`type`·`due`:** `repeat`에서 파생되는 레거시 값입니다(`'무기한'`/`'일회성'`, `'2099-12-31'`). 프론트 코드에도 "삭제 예정"으로 표시돼 있어, 서버에서 쓰지 않으면 제거할 수 있습니다.
- **`day`:** `nextDate`의 요일과 같은 값이라 두 값이 어긋날 수 있습니다. 서버에서 계산하는 편이 안전합니다.
- **`teamName`:**
  - 클라이언트가 보낸 이름을 그대로 저장하고, 팀 이름이 바뀌면 `updateMany`로 맞춥니다.
  - 서버가 `teamId`로 이름을 채우거나 `populate`로 조인하면 불일치가 생기지 않습니다.
  - `teamId`도 `String` 대신 `ObjectId`와 `ref: 'Team'`으로 두면 좋습니다.

### D4. `GET /notes`가 조회하면서 삭제 🟡
- **현재:** 목록을 조회할 때마다 8일 지난 한마디를 `deleteMany`합니다. 화면 문구는 "일주일 후 자동 삭제"입니다.
- **제안:**
  - MongoDB TTL 인덱스(`createdAt`에 `expires: '7d'`)로 DB가 알아서 지우게 합니다. GET은 읽기만 합니다. 기간도 화면 문구와 맞춥니다.
  - 사소한 것: 100개 제한을 개수를 센 뒤 저장하는 방식으로 확인해, 동시 요청이 들어오면 조금 넘을 수 있습니다.

### D5. 공지 개수 제한 ⚪
- **현재:** 서버의 공지 등록에는 개수 제한이 없습니다. 그런데 프론트의 등록 실패 문구는 "너무 많아서 그럴지도요. 100개까지만 돼요"입니다 (한마디 문구를 그대로 쓴 것으로 보입니다).
- **협의:** 서버에 제한을 추가할지, 프론트 문구를 고칠지 정해 주세요.

## 🔌 API 설계

### A1. 응답 형식 통일 🟡
- **현재:**
  - 404 본문: `{ id: -1 }`, `{ error: '...' }`, `false`가 섞여 있습니다.
  - 500 본문: 텍스트와 JSON이 섞여 있습니다.
  - 생성 성공: 공지만 201이고 나머지는 200입니다.
- **제안:**
  - 에러는 한 형식으로 통일합니다. 예: `{ "error": { "code": "TEAM_NOT_FOUND", "message": "..." } }` 또는 표준인 RFC 9457(Problem Details).
  - 생성은 `201`, 삭제는 `204`로 맞춥니다.
- **프론트 영향:** 3단계에서 404를 "이미 삭제됨" 처리에 쓰기 시작합니다. 상태 코드만 유지되면 본문 형식이 바뀌어도 영향이 작습니다.

### A2. REST 경로 정리 ⚪
- `PUT /team?id=` → `PUT /teams/:id` (ID는 경로에 둡니다)
- `/team`·`/teams` 혼용 → 복수형(`/teams`)으로 통일합니다.
- 존재 확인 전용 `GET /team/:id`(true/false) → 리소스를 돌려주는 `GET /teams/:id`로 바꿉니다. 프론트는 3단계에서 존재 확인 호출을 대부분 없애고 404 처리로 바꿉니다.
- 부분 수정이면 `PATCH`를 씁니다.
- B1(서버 측 PIN 검증)을 고칠 때 변경 요청에 PIN을 담고, 틀리면 `403`을 주면 됩니다. 그러면 `check-*-pin`은 "입력 중 즉시 확인" UX에만 필요합니다.
- **프론트 영향:** 프론트는 API 호출을 `src/api/` 한 곳에 모아 두었습니다. 경로가 바뀌어도 그 파일들만 고치면 됩니다. 바꾸는 시점을 알려 주세요.

## ⚙️ 운영

### O1. 로그 쓰기 방식 🟡
- **현재:** 요청마다 `log.txt`(최대 5만 줄) 전체를 읽고 한 줄을 추가해 다시 씁니다.
- **문제:**
  - 매 요청이 느려집니다.
  - 요청이 동시에 오면 서로 덮어써서 로그 줄이 사라집니다.
  - 입력값에 줄바꿈이 있으면 로그 줄이 깨지거나 위조됩니다.
- **제안:**
  - `fs.appendFile`과 로그 로테이션을 쓰거나, `pino` 같은 로거를 씁니다.
  - 형식은 JSON 한 줄로 합니다.
  - 또는 DB 컬렉션에 TTL 인덱스를 붙여 저장합니다.

### O2. 방문 기록이 `GET /teams`에 붙어 있음 🟡
- **현재:** `GET /teams`를 호출할 때마다 `pageload` 로그를 남깁니다.
- **프론트 영향:** 프론트 3단계에서 "탭으로 돌아오면 데이터 다시 불러오기"를 켭니다. 그러면 **같은 방문자의 `pageload`가 지금보다 많이 기록됩니다.**
- **제안:** 방문 기록을 `POST /visits`처럼 따로 분리합니다. 프론트는 페이지 진입 때 한 번만 호출하면 됩니다. 분리 전까지는 집계할 때 감안해 주세요.

### O3. 인증서 갱신 🟡
- **현재:** Node가 시작할 때 Let's Encrypt 인증서 파일을 한 번만 읽습니다. 인증서가 90일마다 갱신돼도 서버를 다시 시작하지 않으면 만료된 인증서를 계속 씁니다.
- **제안:**
  - TLS는 Caddy(자동 갱신)나 nginx 같은 리버스 프록시에 맡기고, Node는 내부 HTTP로 돌립니다. URL의 `:8081`도 없앨 수 있습니다.
  - 당장은 certbot의 갱신 후크(`--deploy-hook`)로 서버를 재시작해도 됩니다.

### O4. 시작·종료 처리 ⚪
- **현재:** DB 연결이 실패해도 `failed`만 출력하고 서버가 뜹니다. 이후 모든 요청이 500이 됩니다.
- **제안:**
  - DB 연결에 성공한 뒤에 `listen`하고, 실패하면 프로세스를 종료합니다 (pm2·systemd가 재시작).
  - `GET /health`를 추가합니다.
  - 종료 신호를 받으면 연결을 정리합니다.

### O5. 팀 삭제 처리 ⚪
- **현재:** 합주를 먼저 지운 뒤 팀을 지웁니다. 중간에 실패하면 합주만 사라집니다. 또 `findById`와 `findByIdAndDelete`로 조회를 두 번 합니다 (다른 삭제 API도 마찬가지).
- **제안:**
  - 팀을 먼저 삭제하거나 트랜잭션을 씁니다.
  - `findByIdAndDelete` 한 번으로 처리하고, 결과가 `null`이면 404를 줍니다.

### O6. 자잘한 정리 ⚪
- `bodyParser.json()`과 `express.json()`이 중복입니다. `urlencoded`는 쓰이지 않습니다.
- `helmet`으로 기본 보안 헤더를 추가합니다.
- `ensembles.teamId`에 인덱스를 추가합니다. 팀 수정·삭제 때 `updateMany`·`deleteMany`가 씁니다. 지금 규모에서는 체감되지 않습니다.
- 팀의 `publishDate`는 클라이언트가 보내고, 공지는 서버가 만듭니다 → mongoose `timestamps: true`(`createdAt`·`updatedAt`)로 통일합니다.
- `PORT` 상수를 선언해 놓고 `listen(8081)`에 숫자를 직접 씁니다.
